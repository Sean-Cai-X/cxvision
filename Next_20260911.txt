  ## 一、当前 C++ YOLOv8 的准确定位

  当前模型是 YOLOv8 风格的 C++ 复刻版本：

  Image
    → YOLOv8-like Backbone
    → PAN Neck
    → P3/P4/P5 Detect Head
    → AABB + class confidence
    → confidence filter
    → class-wise NMS
    → class-agnostic NMS

  它与成熟 YOLOv8 仍有差异：

  - 当前是直接四通道 box regression，未启用标准 DFL。
  - TAL 当前按 P3/P4/P5 分别执行，不是全尺度统一 assignment。
  - 没有 EMA、warmup、LR scheduler 等完整训练机制。
  - 没有 OBB angle regression。
  - 没有独立 objectness 分支。
  - 当前 7 个几何类别直接在每个空间位置分类。
  - 输入只有 128×128，细线、弧线和相似轮廓容易在下采样中丢失。

  因此它可以作为受控增量和链路闭环基础，但目前还不能视为成熟 YOLOv8 的等价替代。

  ## 三、当前问题最应优先修改什么

  当前数据每张图只有一个对象，但候选模型平均输出约 3.6～3.8 个检测框。失败样本进一步表明，主要问题是分类混淆和多尺度重复响应，而不是单纯定位失败。

  当前优先级应为：

  ### P0：先修测试和业务推理契约

  受控案例是一 ROI 一目标，应支持：

  expected_instances_per_roi = 1
  selection_policy = TOP1_PER_ROI

  而不是：

  postprocess_max_detections = 20

  离线检查表明，按单目标 Top-1 处理后，候选 F1 可以从约 0.27 提升到约 0.60～0.64。

  但这只是推理契约对齐，不算模型训练质量提升。正式流程必须：

  validation 选择阈值
  → 固化 inference profile
  → holdout 仅验证一次

  不能利用 holdout 反复调参。

  ### P1：把 assignment 修成完整的全尺度 TAL

  YOLOv8 是 anchor-free，但仍存在 P3/P4/P5 网格 anchor points。正确流程应是：

  P3/P4/P5 原始预测
  → 统一解码
  → 拼接全部 anchor points
  → GT 内候选过滤
  → alignment metric
  → 全尺度 Top-K
  → 多 GT 冲突消解
  → normalized alignment target score
  → 分类和 box loss

  当前逐尺度 Top-K 会让一个 GT 在多个尺度分别形成正样本，容易制造多个高置信响应。

  这是当前最重要的核心训练修复。

  ### P2：恢复标准 DFL Box Head

  当前直接回归：

  x, y, width, height

  应升级为：

  4 × reg_max logits
  → Distribution Focal Loss
  → anchor point + stride 解码
  → xyxy

  这会改变 Head 参数形状，因此不能覆盖现有模型版本，必须形成新模型谱系：

  cpp_yolov8_direct_box_v1
    → cpp_yolov8_dfl_global_tal_v2

  旧模型仍作为回滚版本。

  ### P3：解决几何类别混淆

  现在主要失败是：

  arc / circle / ellipse / open_curve / polygon / rectangle

  之间的分类混淆。仅依赖 YOLO 空间位置上的分类 Head 不一定是最佳业务结构。

  更适合当前业务的路线可能是：

  公共定位模型
    → 获取单目标 ROI
    → 高分辨率 ROI 分类器
    → 类型对应的几何/分割处理

  也就是把“在哪里”和“是什么类型”拆开：

  Detector：geometry_object，负责定位
  Classifier：7 类，负责类型判定
  Geometry Head：负责角度、中心、尺寸和残差

  ROI 分类器可以独立考虑：

  - Adaptive Average Pooling；
  - Max Pooling；
  - Avg + Max 拼接；
  - GeM pooling；
  - 小型 attention pooling。

  但池化修改应发生在 ROI 分类器，不建议为了分类混淆直接重写整个 YOLO Backbone 的池化方式。

  ## 四、什么时候需要修改卷积层和 Route

  ### 增加 P2 检测层

  对于 128×128 输入，P3 stride=8 的特征图只有 16×16。细线、短弧、弱边界可能在 Backbone 下采样时损失。

  可以增加：

  P2 stride=4
  P3 stride=8
  P4 stride=16
  P5 stride=32

  P2 更适合小目标和细线，但代价是：

  - anchor point 数量增加；
  - 显存和推理时间增加；
  - 背景响应和误报可能增加；
  - 必须配合全尺度 TAL 和更严格的负样本训练。

  因此 P2 应在完成全尺度 TAL 后评估，不能在当前重复 assignment 仍存在时直接加入。

  ### 修改卷积/下采样

  只有在证据证明细节在 Backbone 早期丢失时，才考虑：

  - stride-2 convolution 改进；
  - anti-aliased downsampling；
  - 更窄或更深的 C2f；
  - dilation；
  - Neck 通道宽度调整；
  - 部分高分辨率残差路径。

  这属于结构升级，不是普通增量微调，应产生新的 architecture version。

  ### 修改 Neck/Route

  当检测位置基本正确、类别不稳定，优先解冻或增强 Neck；当小目标特征不足，再修改 P2/P3 route。

  推荐逐级推进：

  L0：只调推理参数
  L1：只训练 Head
  L2：训练 Neck + Head
  L3：解冻 Backbone 后部 + Neck + Head
  L4：修改 P2/P3/P4/P5 route
  L5：修改完整 Backbone 或模型家族

  每一级都必须与上一层做固定集对照，不能直接从 Head-only 跳到全模型重构。

  ## 五、OBB 应形成独立模型路线

  当前 OBB 是确定性后处理几何头：

  accepted ROI
  → segmentation mask/contour
  → min-area rectangle / geometry fit
  → center、width、height、angle、residual

  它可以提升业务最终几何结果，但前提是检测 ROI 已经正确。它不能解决错误类别和错误目标。

  未来如需真正的 YOLO OBB，应建立新 track：

  YOLO OBB Head
  → cx, cy, width, height, angle
  → rotated IoU loss
  → rotated Task-Aligned Assignment
  → rotated NMS

  同时数据集必须增加真实 OBB 标签，不能从现有五列 AABB 标签直接宣称 OBB 训练成立。

  建议保留两个明确路线：

  - O1-POST_GEOMETRY：AABB/Segmentation 后确定性 OBB，适合测量和可解释业务。
  - O2-LEARNED_OBB：模型直接预测 angle，适合密集旋转目标。

  两者结果、指标和模型制品必须分开。

  ## 六、面向不同业务案例的模型池设计

  后续不应为每个案例复制一套模型，而应按能力建立模型池：

  Model Family
  ├── D1：单目标 ROI AABB Detector
  ├── D2：多目标 AABB Detector
  ├── C1：Geometry Type Classifier
  ├── S1：Geometry Segmentation
  ├── O1：Deterministic OBB Geometry Head
  └── O2：Learned OBB Detector

  案例通过资产声明需求：

  {
    "task_profile": "single_roi_geometry",
    "expected_instances_per_roi": 1,
    "detector_family": "D1",
    "classifier_family": "C1",
    "geometry_head": "O1",
    "required_outputs": [
      "class",
      "confidence",
      "center",
      "width",
      "height",
      "angle_deg",
      "fit_residual"
    ]
  }

  C++ 只能解释通用 schema，不允许按案例名选择特殊 route。

  ## 七、持续训练与生产升级流程

  每一轮优化必须按以下顺序推进：

  1. 失败样本分类
  2. 判断属于数据、推理参数、Head、Neck、Backbone、Route 或 Geometry Head
  3. 创建单一变量的 Candidate Recipe
  4. 从明确父模型初始化
  5. 记录加载、缺失、shape mismatch 和冻结范围
  6. 完整训练集训练
  7. Validation 做 checkpoint 和阈值选择
  8. 固定阈值后评估困难样本和 holdout
  9. 与当前 Active、父模型和历史 baseline 对照
  10. 生成候选制品、签名、证据包和回滚版本
  11. Headless 技术准入
  12. 业务端验证后决定 Approved/Active

  不同修改的兼容性要明确：

   修改类型               可否沿用原 checkpoint    模型谱系处理
  ━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   阈值、Top-K、NMS       可以                     同模型、新 inference profile
  ─────────────────────  ───────────────────────  ─────────────────────────────────────────
   Loss、全尺度 TAL       可以                     新训练 Candidate
  ─────────────────────  ───────────────────────  ─────────────────────────────────────────
   解冻 Neck/Backbone     可以                     新 fine-tune stage
  ─────────────────────  ───────────────────────  ─────────────────────────────────────────
   DFL Head               Head 形状变化            Backbone/Neck 部分迁移，新 architecture
  ─────────────────────  ───────────────────────  ─────────────────────────────────────────
   增加 P2 route          Neck/Head 变化           新 architecture
  ─────────────────────  ───────────────────────  ─────────────────────────────────────────
   新 OBB Head            Head/标签/输出变化       新 task family
  ─────────────────────  ───────────────────────  ─────────────────────────────────────────
   单独 ROI Classifier    不共用检测 Head          新组合模型 route

  ## 八、生产界面参数分层

  不是所有参数都应该允许业务人员随意修改。界面建议分三层：

  1. 业务安全参数：

  confidence threshold
  expected instances per ROI
  Top-K
  NMS IoU
  ROI
  class allowlist

  2. 训练高级参数：

  epochs
  full batches per epoch
  learning rate
  scheduler
  warmup
  freeze stage
  assignment Top-K
  loss weights
  early-stop

  3. 架构只读参数：

  Direct Box / DFL
  P2/P3/P4/P5 route
  Backbone variant
  Neck width
  OBB/Segmentation branch
  output contract
  parent compatibility

  每次运行后界面必须回显：

  请求值
  实际生效值
  来源资产
  模型版本
  父模型
  训练阶段
  checkpoint selection
  阈值 profile
  评估结果
  准入状态

  最终路线应当是：

  成熟父模型
  → 推理契约校准
  → 全尺度 TAL + DFL 候选
  → ROI 分类增强
  → 按证据决定是否增加 P2/解冻 Neck
  → 独立 OBB/Segmentation 几何评价
  → 固定验证与 holdout
  → 版本化发布和回滚

  这样既能解决当前低 F1、高误报问题，也能保证后续不同案例不会演变成大量不可维护的模型分支和 C++ 特例。
  
  
  
  理解一致：调参路径必须与分类观测绑定，但不能让每次增量训练都重新人工探索。应先固化一套“分类观测 → 自动诊断 → 有界调优 → 固定集验证 → 模型发布”的默认流程，
  后续案例只做小范围扩展。

  ## 一、先冻结七类分类语义

  当前业务分类固定为：

  线
  弧线
  圆
  椭圆
  多边形
  开放曲线
  封闭曲线

  需要注意，现有模型类别为：

  arc, circle, ellipse, line, open_curve, polygon, rectangle

  现有 rectangle 与新的 closed_curve 不一致，不能静默替换。为保持父模型类别索引兼容，建议保留已有 ID：

  0 = arc
  1 = circle
  2 = ellipse
  3 = line
  4 = open_curve
  5 = polygon
  6 = closed_curve

  其中：

  - UI 可以按业务习惯显示“线、弧线、圆……”；
  - 内部 class ID 不能因为显示顺序变化而重排；
  - 原有 rectangle 样本需要明确迁移为 polygon、closed_curve 或保留为子类型；
  - 如果 rectangle 与 closed_curve 都要独立识别，就应升级为 8 类新模型，不能复用七类 Head 冒充兼容。

  ## 二、调优与分类观测如何绑定

  不是“每个类别拥有一套独立 YOLO”，而是：

  共享模型参数
      +
  按类别统计的观测结果
      +
  按类别生成的调优动作

  参数分成四层：

   参数层          范围                                                         是否自动调优
  ━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   推理校准        每类 threshold、Top-K、NMS、expected instances               可以自动
  ──────────────  ───────────────────────────────────────────────────────────  ────────────────────────────────────────
   训练超参数      LR、class weight、采样比例、focal gamma、assignment Top-K    可以在有界范围自动搜索
  ──────────────  ───────────────────────────────────────────────────────────  ────────────────────────────────────────
   网络训练范围    Head、Neck、Backbone 解冻阶段                                按规则自动升级
  ──────────────  ───────────────────────────────────────────────────────────  ────────────────────────────────────────
   网络结构        DFL、P2 route、OBB/Seg 分支、卷积和池化结构                  不在每轮自动修改，必须升级 recipe 版本

  分类观测必须至少输出：

  per-class precision
  per-class recall
  per-class F1
  confusion matrix
  confidence distribution
  localization IoU
  duplicate count
  miss count
  false-positive count
  hard-sample list
  geometry residual
  inference latency

  然后自动诊断：

  重复框高
  → assignment / Top-K / NMS

  类别混淆高
  → class weight / hard negative / ROI classifier

  定位差
  → DFL / box loss / input size

  细线或小目标漏检
  → P2 route / resolution / Neck

  旋转几何残差高
  → segmentation / OBB geometry head

  整体域偏移
  → 解冻 Neck，再决定是否解冻 Backbone

  ## 三、默认自动增量调优流程

  建议固化为 GEOMETRY_INCREMENTAL_AUTO_TUNE_V1：

  资产与类别预检
      ↓
  父模型固定集基线推理
      ↓
  生成七类观测矩阵
      ↓
  自动分类 GAP
      ↓
  推理参数校准
      ↓
  Head-only 增量训练
      ↓
  必要时升级 Neck + Head
      ↓
  固定 Validation 选择模型与参数
      ↓
  困难样本回归
      ↓
  Holdout 单次确认
      ↓
  生成 Candidate、证据包和回滚模型

  ### 阶段 A：资产与类别预检

  自动验证：

  - 七类全部存在；
  - class ID 与父模型一致；
  - train/validation/holdout 来源隔离；
  - 每类样本数和增强分布完整；
  - ROI、AABB、mask、geometry 标签完整；
  - rectangle/closed_curve 不存在歧义；
  - 没有把同源增强样本分到不同集合。

  输出：

  CLASS_ONTOLOGY_PASS
  DATASET_PREFLIGHT_PASS
  class_distribution.json
  source_split_audit.json

  ### 阶段 B：父模型分类观测

  父模型必须先在固定 validation 上运行，生成：

  confusion_matrix.json
  per_class_metrics.json
  confidence_distribution.json
  duplicate_anchor_report.json
  localization_failure_report.json
  geometry_residual_report.json

  每类结论示例：

  line:
    recall_low
    classification_ok
    localization_ok

  arc:
    confused_with_open_curve

  circle:
    confused_with_ellipse

  closed_curve:
    confused_with_polygon

  这些事实才是自动调优输入。

  ### 阶段 C：无训练推理校准

  先搜索不改变模型权重的参数：

  global confidence threshold
  per-class confidence threshold
  NMS IoU
  per-ROI Top-K
  expected_instances_per_roi
  class allowlist

  当前一 ROI 一对象案例默认：

  expected_instances_per_roi = 1
  selection_policy = TOP1_PER_ROI

  此阶段如果已经满足业务门槛，就不启动训练。

  ### 阶段 D：Head-only 自动增量训练

  需要训练时，默认先执行：

  全尺度 TAL
  DFL Box Head
  分类 Quality Target
  困难类别采样
  困难负样本注入
  Head-only
  完整数据 epoch
  validation-best checkpoint

  自动候选不宜过多，建议每轮最多 3 个：

  Candidate A：基准训练参数
  Candidate B：分类混淆加强
  Candidate C：召回/定位加强

  系统根据七类观测自动配置：

  - arc ↔ open_curve 混淆：增加对应 hard negatives；
  - circle ↔ ellipse 混淆：增加长宽比和轮廓形态边界样本；
  - polygon ↔ closed_curve 混淆：增加角点、曲率和闭合性边界样本；
  - line 漏检：提高细线样本权重，必要时进入 P2 评估。

  ### 阶段 E：自动决定是否扩大训练层

  默认决策规则：

  Head 改善明显
  → 保持 Head-only

  Head 分类仍差、定位正常
  → Head + Neck

  小目标/细线特征不足
  → 新建 P2 architecture candidate

  全类别同时退化
  → 检查数据域，再评估 Backbone 后部解冻

  旋转/几何残差差
  → 进入 OBB/Segmentation route

  每次只能升级一级，不允许一次性解冻全模型。

  ## 六、后续增量训练不再重复探索

  首轮需要把以下内容固化：

  1. 七类 ontology 和稳定 class ID。
  2. 默认数据完整性规则。
  3. 默认分类混淆对。
  4. 默认推理参数搜索范围。

  8. 自动 early-stop 和 checkpoint 策略。
  9. 生产质量门槛。
  10. 证据包和回滚格式。

  后续新案例只需要提供：

  新增图片
  ROI
  七类标签
  来源
  困难样本标记
  业务质量门槛

  系统自动复用流程，不再由人工重新决定“先调 threshold 还是先改 loss”。

  ## 七、最终发布状态流

  REFERENCE_ONLY
  → TRAINING_READY
  → AUTO_TUNING
  → CANDIDATE
  → EVALUATED
  → HEADLESS_APPROVED
  → 业务端验证
  → APPROVED
  → ACTIVE

  任何类别出现以下情况都应阻止升级：

  关键类别漏检率超限
  某类别相对 Active 明显退化
  holdout 误报增加
  分类 ontology 不一致
  推理 profile 未锁定
  模型和参数回执不完整
  回滚模型不可验证

  最终应形成的是“一条默认七类几何增量模型流水线”，而不是每次案例都重新手工调 YOLO：

  七类固定观测
  → 自动推理校准
  → 自动 Head 增量
  → 按证据扩大到 Neck/Route
  → 独立几何头整定
  → 固定集回归
  → 可追溯发布

  这套默认流程先覆盖现有七类，后续新增类别、P2、真正 OBB 或新 Backbone 时，只通过新的 ontology/recipe/model-family 版本微扩展。
  
  
  把已确认的七类几何增量方法流落为资产驱动的首版自动调优闭环；先覆盖无需改网络结构即可自动执行的观测、阈值/Top-K 搜索、类别诊断和下一训练 recipe，再接入
    UI 与 headless 验证。
    □ 定义稳定七类 ontology、显式旧类迁移和自动调优 policy schema
    □ 实现 headless 自动调优执行器：预检、分类观测、阈值/Top-K 搜索、holdout 锁定验证
    □ 生成训练升级建议与版本化证据/回滚状态
    □ 接入 Torch UI：默认流程、参数、阶段和有效结果反馈
    □ 编译并在现有 validation/holdout 证据上执行 headless 验证
    □ 运行静态/UI 审计并归档交接结论
    
    
    
    • 自动调优执行器不应直接照搬 Darknet 的单一 cfg 文本界面。更合适的方案是：

  - JSON Schema 作为唯一配置源，负责默认值、类型、范围、搜索空间和版本。
  - GUI 提供结构化参数控件。
  - 提供“Darknet cfg 风格”的高级只读配置预览，方便算法人员整体核对。
  - 每次执行生成不可变的 effective config、运行命令、Hash、指标和选择回执，保证可分析、可重放。

  ## 七、状态边界

  自动调优执行器可以自动得出：

  AUTO_TUNE_READY
  AUTO_TUNE_RUNNING
  AUTO_TUNE_EVALUATED
  TRAINING_RECIPE_REQUIRED
  QUALITY_GATE_FAILED
  HANDOFF_READY

  但不能因为搜索出更好的阈值就自动显示 APPROVED 或 ACTIVE。

  对于当前模型，合理语义是：

  模型状态：CANDIDATE
  调优状态：EVALUATED
  生产状态：NOT_APPROVED
  原因：分类混淆、漏检率或误报率仍未达到策略阈值

  最终落地形态应当是：结构化 GUI 控件负责调参，JSON 负责唯一配置事实，cfg 风格页面负责整体核对，headless 执行器负责真实验证，Evidence 页面负责回执、质量结论
  和回滚。
  
  
   执行流程是：

  资产/标注/ROI 预检 → 冻结七类本体校验 → Validation 阈值×TopK 搜索 → 固化最优后处理配置 → Holdout 一次确
  认 → 困难样本/回归评估 → 输出训练配方、证据索引、回滚信息 → 质量准入结论

  七类固定为：arc、circle、ellipse、line、open_curve、polygon、closed_curve。历史 rectangle 已要求显式迁移
  为 closed_curve，不会静默混用。

  当前执行器已完成的事实：

  - 验证集仅用于选择后处理参数；Holdout 不参与调参，避免数据泄漏。
  - 当前选出的有效推理配置：confidence=0.50、TopK per ROI=1。
  - Validation 候选 F1：0.602041，优于父模型 0.591837。
  - Holdout 候选 F1：0.639175，优于父模型 0.591837。
  - 已生成可追溯的 requested_config、effective_config、混淆矩阵、Holdout 确认、下一轮训练配方与证据索引。
  - 当前执行结论：AUTO_TUNE_EVALUATED，不是批准或激活。

  不能发布的原因是质量门仍失败：

  - Holdout 漏检率约 0.367347，高于准入上限 0.25。
  - Holdout 误报案例率约 0.346939，高于准入上限 0.25。
  - 因此当前质量状态是 QUALITY_GATE_FAILED，生产准入状态为 REJECTED。

  所以准确状态应为：训练与评估链路已经具备业务交付能力，模型本身仍是“已评估、待质量修复”的候选，不是
  APPROVED 或 ACTIVE。即使人工签署暂时 bypass，也不应绕过漏检和误报这两个基础质量门；否则会把已知缺陷带入
  业务推理。
  
  
  长边界不能只靠“局部像素像不像一条线”，因为沿线有大量重复纹理、相近梯度和相同曲率；如果没有锚定区域，模型会出现漂移、重复高置信候选，或把相邻边界误连为
  同一条。

  应采用“三层 ROI”而不是单一检测框：

   层级            作用                               选择原则
  ━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   context_roi     确认所在工件/区域及两侧材料关系    覆盖足够大上下文，包含边界两侧区域
  ──────────────  ─────────────────────────────────  ─────────────────────────────────────────────────────────────
   anchor_roi      确认“这是哪一段边界”               优先端点、交点、拐点、曲率极值、缺口端、纹理/颜色变化显著处
  ──────────────  ─────────────────────────────────  ─────────────────────────────────────────────────────────────
   boundary_roi    做局部几何拟合与连续性判断         沿边界展开的窄带，不单独承担身份识别

  锚定区域不能按固定坐标写死，应由案例资产提供候选锚点，并用可判别性选择：

  1. 边界两侧对比度足够；
  2. 局部曲率、方向或拓扑有区分度；
  3. 含端点、连接点、孔洞、角点、缺口端等稳定结构时优先；
  4. 与其他候选锚点的视觉相似度低；
  5. 经模糊、色变、缩放、旋转后仍可定位；
  6. 不能只落在一段无限长、笔直且完全重复的边界中间。

  对于不同类别：

  - line：优先选线段端点、交叉/接触点，或两侧纹理/颜色发生变化的位置；纯直线中段只用于拟合，不能单独做锚定。
  - arc / ellipse / circle：优先曲率稳定且与邻接轮廓关系明确的位置；圆弧端点、与直线/区域交接处优先。
  - open_curve：优先两个端点、曲率变化点和缺口两端；中段仅作为连续性支持。
  - polygon / closed_curve：优先顶点、边界连接关系和局部凹凸特征，而非任一平直边段。

  训练与推理闭环应是：

  context_roi 定位区域
  → anchor_roi 确认边界身份与起始约束
  → boundary_roi 沿局部边界搜索/拟合
  → 连续性、方向、两侧区域一致性复核
  → 输出唯一几何实例

  数据资产需要新增并版本化：

  - anchor_candidates.json：候选锚点及来源事实；
  - anchor_roi、context_roi、boundary_roi；
  - anchor_discriminability_score；
  - anchor_stability_matrix：模糊、色变、缩放、旋转、缺口下的可定位率；
  - boundary_continuity_contract：允许断开长度、最大漂移、连接方向和两侧一致性规则。

  这样锚点负责“认出是哪一条边界”，几何头负责“精确量出这一段边界”。这也正是当前 OBB/YOLO 检测头之外，边界业务发布必须补上的约束层。
